# v1.9 Feasibility Report — Regional Terrain & Per-Epoch Frame Transformation

**Date:** 2026-11-07 · **Status:** RESEARCH ONLY — no new capability claimed.
**Decision:** CHANDRA keeps (a) the **LOCAL HORIZON** model and label, and (b) the
**constant ME/PA→IAU rotation with the 2020–2035 validation gate**. This report
documents what a safe implementation would require, with authoritative sources.
Nothing below is implemented; metadata fields are not capability claims.

---

## 1. Regional (distant-horizon) terrain from PGDA LOLA products

### 1.1 What the authoritative products actually are

NASA Goddard's Planetary Geology, Geophysics and Geochemistry lab (PGDA) publishes
the current reference south-polar topography ("A New View of the Lunar South Pole
from LOLA", product page `https://pgda.gsfc.nasa.gov/products/90`; peer-reviewed
method: Barker et al. 2023, *Planet. Sci. J.*, DOI `10.3847/PSJ/acf3e1`, published
2023-09-29; data DOI `10.60903/gsfcpgda-lola-spole`):

| Product | Content | Size | Notes |
|---|---|---|---|
| `LDEM_80S_20MPP_ADJ.TIF` | surface height (m) | 2.6 GB | 80–90°S, 20 m/pixel |
| `LDEM_80S_20MPP_ADJ_ERR.TIF` | height error (m) | 3.7 GB | per-pixel uncertainty |
| `LDEM_80S_20MPP_ADJ_EFFRES.TIF` | effective resolution (m) | 3.8 GB | true resolving power |
| `LDEC_80S_20MPP_ADJ.TIF` | LOLA spot counts per pixel | — | sampling density / interpolation flag |
| `LDSM_80S_20MPP_ADJ.TIF` | slope (deg) | 3.6 GB | derived |

- **CRS:** south polar stereographic, X/Y in **meters**, ±304 km range (Barker et
  al. 2023, Table 1). Not geographic lat/lon — ingestion must reproject.
- **Frame/datum:** **MOON_ME of the JPL DE421 ephemeris** (PGDA product page).
  Heights are surface heights in meters relative to the product's reference
  radius; the spherical reference radius (1737.4 km) must be read from the file
  metadata, never assumed per-product.
- **Resolution caveat:** the *effective* resolution is ~20 m/pixel only poleward
  of ~84°S; equatorward of that the grid is increasingly interpolated (Barker et
  al. 2023 §2; Gläser et al. 2014 found ~22.7% interpolated pixels in a
  160×160 km 20 m/pixel polar DTM). A regional horizon must carry the EFFRES/LDEC
  layers as provenance, not just the elevation grid.
- **NoData:** pixels without LOLA coverage exist and must be treated as NoData —
  CHANDRA's rule (never invent elevations; incomplete coverage blocks
  quantitative visibility) already covers the local pipeline and would extend
  unchanged to regional rays.

### 1.2 Why it is NOT implemented in v1.9

1. **Data access:** `pgda.gsfc.nasa.gov` is not reachable from this build
   environment (egress allowlist), and the project's CI policy forbids
   unavailable NASA downloads. The 2.6–3.8 GB COGs cannot be fetched, checksummed
   or windowed-read here. No regional coverage is manufactured to compensate.
2. **Validation burden:** a regional distant-horizon model changes every
   visibility number. Acceptance would require comparison against published
   illumination results (e.g. the Connecting Ridge studies of Gläser et al.,
   which used 20 m/pixel adjusted LOLA DTMs and 50×50 km regions) before any
   user-facing claim.
3. **Honest scope:** the current ray-marched crop (radius ≤ 20 km) is labeled
   **LOCAL HORIZON** everywhere — UI, reports (`localHorizonDisclosure`), and
   docs. Obstructions beyond the crop are explicitly not captured.

### 1.3 Acceptance plan if access becomes available

1. Offline ingestion tool (extends `terrain_api`): windowed COG reads via
   rasterio; stereographic→planetocentric reprojection; read reference radius,
   frame, NoData sentinel and EFFRES/LDEC from the actual file; record SHA-256,
   product version and crop bounds in provenance.
2. Distant-horizon ray march out to a disclosed regional radius (e.g. 50–300 km),
   per-ray coverage accounting; any NoData ray blocks quantitative use (existing
   `INCOMPLETE_COVERAGE` gate).
3. Parity validation: reproduce at least one published illumination/visibility
   result within its stated uncertainty; publish the comparison in VERIFICATION.
4. Only then: change the label from LOCAL to REGIONAL, with the crop radius,
   effective resolution and error layer disclosed per site. Until every step
   passes, the LOCAL HORIZON label stays.

## 2. Per-epoch (time-dependent) lunar frame transformation

### 2.1 Authoritative method

NAIF's lunar frames kernel `moon_080317.tf` (JPL/NAIF, fetched 2026-11-07 via
`https://naif.jpl.nasa.gov/pub/naif/pds/pds4/ladee/ladee_spice/spice_kernels/fk/moon_080317.tf`)
defines:

| Frame | ID | Realization |
|---|---|---|
| `MOON_PA` | 31000 | alias of `MOON_PA_DE421` |
| `MOON_ME` | 31001 | alias of `MOON_ME_DE421` |
| `MOON_PA_DE421` | 31006 | **PCK class 2** — time-dependent orientation from the binary PCK (`moon_pa_de421_190625.bpc`) relative to ICRF/J2000 |
| `MOON_ME_DE421` | 31007 | **FIXED** rotation relative to `MOON_PA_DE421` (constant TKFRAME matrix in the FK) |

The rigorous per-epoch position transformation is `PXFORM('MOON_ME','IAU_MOON',
ET, M)` (state: `SXFORM`), requiring the binary PCK + lunar FK + leapseconds
kernel (NAIF PCK tutorial, `19_pck.pdf`; NAIF "High Accuracy Orientation"
tutorial, ESA SPICE workshop 2012-04). Key authoritative cautions:

- Binary PCK coverage is **finite** — the valid time span must be queried from
  the loaded kernels and gated; never extrapolate (NAIF PCK tutorial).
- `IAU_MOON` (text-PCK IAU model) is **less accurate** than the binary-PCK ME/PA
  frames; the ME↔IAU difference is time-dependent (NAIF 2012 tutorial). The FK
  itself notes ME implementations differing by ~0.0051° amplitude (~155 m surface
  equivalent) over ~2000–2020 — the same order as CHANDRA's disclosed constant-
  rotation residual (≤0.0039°, measured by our own SPICE parity over 2020–2035).

### 2.2 What CHANDRA does today (unchanged in v1.9)

- Ephemeris frame: IAU 2015 Moon rotation (astronomy-engine `RotationAxis` +
  `Libration`), light-time corrected.
- DEM imports: explicit allowlist (`MOON_ME`/`MOON_PA` with DE421, IAU 2015 Moon);
  recognized ME/PA masks are rotated by a **constant** rotation whose residual
  (≤0.0039°) was measured against SPICE DE421 + `moon_pa_de421` + `pck00008`
  (tests/data/frame-reference.json, 26 independent SPICE tests).
- The constant correction is **gated to 2020–2035** (`frameIntervalValidated`);
  outside it, `FRAME_MODEL_OUTSIDE_VALIDATED_RANGE` blocks quantitative
  visibility. Unknown frames are never accepted (`FRAME_UNVERIFIED`).

### 2.3 Why per-epoch is NOT implemented in v1.9

The browser engine is TypeScript; there is no validated JS reader for binary
PCKs. The two credible paths both need validation work that cannot be completed
safely in this environment (NAIF hosts are outside the egress allowlist; kernels
are fetched only in the dedicated CI job):

1. **Precomputed rotation tables** (SPICE-generated matrices on an epoch grid,
   interpolated in JS): requires proving an interpolation-error bound against
   dense SPICE sampling across the whole supported range, plus kernel-coverage
   gating baked into the table metadata.
2. **WASM SPICE**: heavy dependency, unvalidated in this project; rejected under
   the "no unnecessary dependencies" constraint without a parity harness.

### 2.4 Acceptance plan (method + evidence required)

1. Extend `tests/python/test_lunar_frame.py` to emit `PXFORM('MOON_ME','IAU_MOON')`
   matrices at ≥daily cadence across the candidate range, from checksummed
   kernels, into a versioned reference fixture.
2. Implement the JS side (table + interpolation), assert agreement with the
   fixture within a disclosed tolerance at *every* fixture epoch, and publish
   the maximum residual (no "conservative" claim without this measurement).
3. Gate to the binary PCK's actual coverage (queried, not assumed); outside it,
   keep blocking — never silent extrapolation.
4. Run the full geometry/parity/browser suites; update SCIENTIFIC_METHOD §11 and
   the report's `ephemeris` block; only then widen or replace the 2020–2035 gate.

Until all four pass, the constant correction + gate remains the only supported
behavior, and the UI/reports say exactly that.
